# Decisions

One line per decision the spec did not settle, with the reason. Newest sections at the bottom.

## Stack and environment (milestone 0)

- D001 Stack changed by Nahom mid-build (prompt updated on main): Railway Postgres + Drizzle, Better Auth, Railway Bucket (S3 API), Railway cron. No Supabase, no Supabase shim, no RLS-on-auth.uid(). Reason: all infrastructure on Railway and GitHub only.
- D002 No Supabase scaffolding had been created before the change (only Next.js + shadcn/ui), so nothing needed removing.
- D003 Libraries used instead of hand-rolled code (Nahom's instruction): date-fns-tz for Addis time, React Hook Form + Zod for forms, TanStack Table for staff lists, browser-image-compression for photo uploads, Better Auth for auth, password hashing and sessions, AWS S3 SDK presigner for signed URLs.
- D004 Next.js pinned to 15.5 (App Router, React 19). Reason: stable, well-known APIs; Next 16 adds churn with no benefit here.
- D005 `.npmrc` sets `legacy-peer-deps=true`. Reason: better-auth declares optional peers for other frameworks (SvelteKit wants vite 8) that clash with vitest's vite range; none of them are used.
- D006 Local database: Docker is available in this environment (daemon started manually), so `scripts/db-start.sh` runs `postgres:16-alpine` in Docker on port 54329. Fallbacks in order: a local Postgres 16 install (`pg_ctl`), then PGlite through `@electric-sql/pglite-socket`. Same Drizzle migrations everywhere.
- D007 Files: `STORAGE_DRIVER=local` (default in dev/test) stores files under `.data/storage/` and serves them through an HMAC-signed, short-lived route; `STORAGE_DRIVER=s3` uses the Railway Bucket with presigned GET URLs (5 minutes). Every read goes through an authorization check before a URL is issued.
- D008 The browser never talks to the database or the bucket directly. All reads and writes go through server components, server actions and route handlers, which call `src/server/authz/` and then services. Reason: one enforcement point; no secrets or SQL client in the bundle; less JavaScript on 3G.
- D009 Business logic lives in services (`src/server/services/`) that take `(ctx: { db, actor, now })` so the same code runs from server actions, job routes, tests and the week simulation with a fake clock.
- D010 Project subagents are written to `.claude/agents/`; because agent definitions load at session start, this session runs them as general-purpose subagents briefed with the exact content of those files.

## Auth and roles

- D011 Staff sign in with email + password (Better Auth emailAndPassword). Clients sign in with phone number + password through Better Auth's phone-number plugin with `requireVerification: false` (no SMS). Each client user gets a synthetic, non-deliverable email `<e164 digits>@clients.questmeals.invalid` because Better Auth requires an email column.
- D012 Staff reset a client's password from the client page; the new password is hashed with Better Auth's own password hasher (`ctx.password.hash`) and written to the client's credential account. No hand-rolled crypto.
- D013 Roles are a text array on the user (`owner`, `operations`, `nutritionist`, `kitchen`, `delivery`, `coach`, `client`). "Coach" is modelled as a role in the set because the spec calls Dagi and Kidus owners "flagged as coaches"; a flag in the role set is the same thing and keeps one permission check.
- D014 Better Auth user ids are UUIDs (`advanced.database.generateId: "uuid"`), stored as `uuid` columns so every table keys on UUIDs.

## Domain interpretations (milestone 0, see PLAN.md section 7)

- D015 Cook date = drop date. Daily and three-drops clients get each service day cooked that day; Sunday's meals are cooked and dropped Saturday when Sunday is not a service day (`sundayWithSaturday`, default on, because the spec's rotation includes Sunday C).
- D016 Only daily delivery and pick-up are enabled by default, matching the package table. Three-drops and every-3-days can be enabled by an owner. Weekly delivery stays in the pricing table (4.33 drops) but cannot be enabled while the freshness rule is 3 days, because a weekly drop would break "delivered no more than 3 days after cooking".
- D017 Quick-start period: from the start date to the end of the week that the first weekly cutoff after the quick-start lock will lock. Example: paid Friday → starts Saturday and is billed through the end of next week, because next week was already locked on Thursday. This extends "service days left in the current week" so a late-week quick start never falls between cycles.
- D018 Quick-start capacity counts reserved starts (issued or paid quick-start invoices) per start date; a full date pushes to the next service date with room.
- D019 When a quick-start payment is confirmed after the 18:00 lock it was quoted for, the start moves to the next available date, the period is recomputed and any difference is kept as an account credit (or amount owed) applied to the next invoice.
- D020 Unpaid = not cooked, per day: at a lock, a meal day is included only if a paid invoice covers it; a week with no covered day is `skipped_unpaid`.
- D021 Billing periods: weekly invoices cover Monday–Sunday; monthly invoices cover calendar months from the start date. Full month = plan price − monthly discount; any other period = round to nearest 10 of (plan price − discount) × service days ÷ 26. The next period's invoice is generated at the Thursday lock that precedes the cutoff it is due at.
- D022 Subscription term defaults to 1 month (1–4 allowed); renewal extends the end date by the term (automatic renewal is phase 2). Price locks for 4 months from the subscription start.
- D023 Body weight stored as integer grams; age stored as entered at intake (whole years).
- D024 Base recipe amounts are numeric with one decimal (the spec has 13.5 g oil); profile portions, stock and purchases are integer grams or pieces.
- D025 On-time delivery = drop marked delivered on its drop date at or before the delivery deadline setting (default 12:00 Addis).
- D026 Savory snack alternative uses 2 eggs, 100 g cucumber and mitmita (seasoning); the cucumber weight was not in the spec.
- D027 Extra protein add-on is a standing add-on per meal slot (applies to that slot's meal every day), priced per portion with the spec formula and added to the client's food cost.
- D028 Gomen → mixed sautéed veg is seeded as cabbage 60% / carrot 40% of the same grams (the Menu A side ratio is 120:80).

## Database, seed, auth and authz (milestone 1, db-engineer)

- D200 (db) `ingredients.slug` (unique, not null) added as the natural key of the reference seed so seeds are idempotent and code/tests can find "chicken-breast" without relying on display names. PLAN.md updated.
- D201 (db) `meals.pantry text[]` holds the recipe-card pantry list from the seed (awaze, garlic, salt…); pantry items are not tracked in stock. PLAN.md updated.
- D202 (db) `swap_rules.to_ingredient_split` is jsonb `[{ ingredientId, fraction }]` with resolved ingredient UUIDs (not slugs); when present it overrides `to_ingredient_id` (gomen → cabbage 0.6 / carrot 0.4).
- D203 (db) The reference seed is insert-if-missing (`on conflict do nothing` by natural key: area name, ingredient slug, meal code, (meal, part name), (part, ingredient), swap code, package code, settings key). Re-running never overwrites staff edits (prices, settings, packages). Extra unique keys added for this: parts(meal_id, name), part_ingredients(part_id, ingredient_id).
- D204 (db) `profile_portions` are seeded by a stub (`db/seed/portions.ts`, qty = computed_qty = round(base) for all six profiles); the lead replaces it with the domain portion engine.
- D205 (db) Demo prices: real ingredient prices are empty, so the pricing formula cannot price anyone yet. Demo subscriptions use the spec's modelled figures — 58,400 ETB/month daily delivery, 54,100 pick-up — with price_day = round(month / 26) (2,246 / 2,081), plan price = month (service fee 0), and `price_breakdown = { demo: true }`.
- D206 (db) Demo calendar (relative to `today`, default Addis today, tests use 2026-10-19): subscriptions start the Monday of the previous week, term 1 month (end = start + 1 month − 1 day), price lock start + 4 months. Weekly billers get one invoice per Mon–Sun week from the start through the week after today's week (past and current paid with a confirmed payment by Nebiyou, next week issued, due Thursday 18:00 Addis = 15:00 UTC of today's week); weekly amount = round10(plan × 6 / 26). Monthly billers get one paid invoice for the first month. The paused client's paused week is not invoiced and their end date moves 7 days.
- D207 (db) Demo nutrition profiles use Mifflin–St Jeor × activity × goal factor, size = nearest of S/M/L kcal, kcal_target and macros at the size's kcal; set by the nutritionist (Hana), not provisional.
- D208 (db) `seedDemo` is skipped when the first demo staff user already exists, so `db:seed` can be re-run safely. `removeDemo` deletes in one transaction: demo/demo-authored community posts, challenges by demo users, demo partner contributions, demo purchases/stock counts, everything of demo clients (orders, drops, invoices, payments, subscriptions, check-ins; the rest cascades), then demo users (sessions, accounts, notifications, Telegram links, comments, reactions, reports, mutes cascade).
- D209 (db) Foreign keys: client-owned rows cascade on client delete; "who did it" user references (`*_by_user_id`, `confirmed_by`, `rider_user_id`, …) are nullable with `on delete set null`, so deleting a (demo) user never blocks on history; reference rows (ingredients, meals, packages) are `restrict`.
- D210 (db) Better Auth rows are written by our own helpers (`createStaffUser`, `createClientUser`, `setUserPassword` in `src/server/auth.ts`) exactly as Better Auth does on sign-up (user + `credential` account with accountId = user id), hashing with `(await auth.$context).password.hash`. Emails are stored lower-case. Client users get phone_number (E.164 `+2519/7XXXXXXXX`) and roles ['client']; the phone validator rejects anything else at sign-in.
- D211 (db) `user.roles`, `isDemo` and `banned` are Better Auth additional fields with `input: false`, so sign-up endpoints can never set roles; `loadActor` returns null for banned users.
- D212 (db) Permissions are fine-grained string keys (`PERMISSIONS` in `src/server/authz`). Interpretations of PLAN §4: swap approval (`swaps.approve`) is owner + nutritionist (spec: anything outside the table needs nutritionist approval; owners see all records); `orders.lock`/`orders.write` are operations only (owners read orders); stock counts and waste are operations + kitchen, purchases operations only; anon may only read the public calculator settings, packages, and create a lead via sign-up. Community access for clients still needs the domain `communityAccess` check on top of `community.*`.
- D213 (db) `homePathFor`: owner → /staff/dashboard, operations or nutritionist → /staff, kitchen → /kitchen, delivery → /delivery, client → /app, coach-only → /app/community, none → /login.
- D214 (db) `invoices.subscription_id` is not null (quick-start and adjustment invoices also hang off a subscription), keeping unique(subscription_id, kind, period_start) meaningful for job idempotency. `notifications.dedupe_key` is unique but nullable (notifications without a dedupe key are allowed). `order_meals` has unique(order_day_id, slot): one meal per slot per day (the savory snack replaces the snack).
- D215 (db) `db` (db/client.ts) and `auth` (src/server/auth.ts) are lazy proxies created on first use and cached on globalThis (survives HMR), so importing them never opens a connection or needs DATABASE_URL at build time. Tests and scripts use `createDb(url)` / `createAuth(db)`.
- D216 (db) Migrations live in `db/migrations` (0000_init generated by drizzle-kit, no hand-written SQL needed: the partial unique index and the coalesce expression index are expressed in Drizzle). `db/migrate.ts` resolves the folder from the repo root (cwd).
- D029 Extra-protein add-on: the per-portion price (spec formula, rounded up to 10) is what the client sees when choosing it; billing uses the plan price, whose food_day already includes the add-on grams as the pricing formula says ("plus swaps and add-ons"), so nothing is charged twice. Adding or removing an add-on re-quotes the plan from the next lockable week.
- D030 Swaps from the swap table within the package limit are approved immediately (status approved); requests outside the table go to the nutritionist (status requested) and do not count toward the limit until approved.
- D100 (domain) `time.ts` does `DateStr` arithmetic on UTC epoch days (no `Date` local getters), so dates never depend on the process time zone; date-fns-tz is used only for instant <-> Addis conversion and formatting. Tests re-run the key assertions under five process time zones.
- D101 (domain) `suggestNutrition` returns integers for storage: bmr, tdee and the goal-adjusted `targetKcal` rounded; macro grams are computed from the chosen size's kcal (what the kitchen cooks), not from the raw target. `bmr`/`tdee`/`goalKcal` stay unrounded (1345.25 for the reference woman).
- D102 (domain) Portion solver: weighted least squares on four rows (day kcal, protein g, carb g, fat g), each weighted 1 / (target × tolerance), with each group factor boxed to [0.6, 1.8]; all 27 free/min/max assignments are solved and the best feasible kept (exact "clamp and re-solve"). Then piece parts are rounded and the gram parts re-solved around them, then clamp-aware rounding (nearest 5 g / whole piece that stays inside 0.6–1.8 × base, e.g. 7 g oil at factor 1.8 -> 10 g not 15 g; a single whole egg always stays 1) and a one-step local search on that grid. Flagged when the rounded day misses ±3% kcal or ±10% on any macro grams. With the seed recipes 7 of 24 are flagged (A S_BUILD, A L_BUILD, B L_BUILD, C M_BUILD, C L_LEAN, C L_BUILD, D L_BUILD): the carb group hits 1.8 (or fat 0.6) before the target is reached, so the nutritionist must edit those cells.
- D103 (domain) Manual portion cells are kept exactly (even outside the clamp) and treated as fixed in the solve; `computedQtyByPartId` for a manual cell is the solver's value for that cell with no manual cells, so the profile table can show both.
- D104 (domain) Quick-start period end = the day before `nextLockableWeek(lock)` where lock is the daily 18:00 lock the evening before the start date (≥ the payment deadline `lockAt`). This follows D017's example (Friday -> through the end of next week) rather than the literal "Sunday of the week locked by the first cutoff after the lock", which would bill one week too many and overlap the client's first weekly order. A lock at exactly Thursday 18:00 is not part of that weekly lock.
- D105 (domain) Monthly billing periods are one-month periods anchored at the start date (22 Oct – 21 Nov), the last clipped to the end date and prorated; a quick-start client's regular billing anchors at quick_start_period_end + 1. `nextInvoicesToGenerate` also returns earlier periods that were never invoiced (catch-up), skips periods with a non-void invoice of the same start and kind or fully covered by other invoices, and sets due = the cutoff of the week the period starts in.
- D106 (domain) Swap quantities: `fixed` and `add` amounts are base amounts scaled by the replaced part's profile ratio (qty ÷ base qty) and rounded to 5 g (2 injera -> 90 g rice; 50 g beans at base 40 -> 75 g beef); `multiply` is exact; `same` keeps qty and unit. Swapped items are named "Original → New" (add: "Beans → extra Lean minced beef") so production rows separate them. Order: slot rules (replacement meal at the client's profile portions, else base) -> ingredient rules by sort (an item made by a swap is not swapped again) -> add-ons (extra protein follows the swapped main protein). Main protein = the gram protein/dairy item with the most grams; a meal without one gets no add-on.
- D107 (domain) Pricing prices seasonings (stevia, cinnamon, milk…) like any ingredient, so a missing seasoning price also blocks publishing ("every ingredient in that client's menu"). Egg whites are costed and buffered as eggs. `priceDayBirr` = Math.round(price_day); price_month rounds the unrounded price_day × 26.
- D108 (domain) `countStandingSwaps` counts swap-table swaps (rule id set) that are approved or requested and in force that week; custom requests never count (compatible with D030). `checkSwapRequest` also answers `duplicate` for a rule already standing.
- D109 (domain) Allergy/dislike matching is case-insensitive at a word start, with the term's singular and a synonym map (fish->tilapia, nuts->peanut, dairy/lactose->yogurt/ayib/feta/mozzarella/milk/cheese, egg->egg whites, gluten/wheat->bread/tortilla/pasta/lasagna, meat->beef/chicken, legumes->beans/peanut, spicy->mitmita/awaze). It checks ingredient names, part names (for swapped items only the new side) and, when nothing else matched and no swap removed the term, the meal name (e.g. "chili"). Oats are not treated as gluten. Over-matching (e.g. "egg" vs "eggplant") is accepted as the safe side.
- D110 (domain) `lockWeek` leaves out cancelled/ended subscriptions and those whose dates miss the week; days that already have an order day (quick start) are not rebuilt; every-3-days clients cook on their group's drop date; eat-by is computed after swaps (tilapia swapped to chicken -> + 3 days).
- D111 (domain) Shopping buys are rounded up to 0.1 kg / 0.1 litre (litre via grams per unit: oil 920, milk 1030) and whole pieces; line cost = buy units × price rounded to whole birr, null = "price missing"; lines fully covered by stock are omitted unless asked for.
- D112 (domain) KPIs: new = clients whose first non-cancelled subscription starts in the month; churn rate = churned ÷ (active + churned − new); MRR = Σ (plan − discount) of active non-quick-start subscriptions; invoiced = non-void invoices issued in the month; collected = payments confirmed in the month; delivery cost = delivery (not pick-up) drops in the month × drop cost; on-time is over delivery drops dated up to today; "no check-in for 14 days" counts from the start date when a client never checked in.
- D113 (domain) Community roles combine by taking the highest level; a mute caps client-derived access at react and does not affect staff access; an ended member keeps read + react through ended_at + 14 days inclusive.
- D114 (domain) Brand contrast (WCAG 2.x) is asserted in `contrast.test.ts`: accent #C2410C on white 5.18, white on accent 5.18, #171717 on white 17.93, #525252 on white 7.81, #FAFAFA on #0A0A0A 18.97, #FB923C on #0A0A0A 8.75 — all AA.
- D115 (domain) `seed-domain.ts` maps the seed reference data to domain types (ids = slugs / meal codes, part ids `${code}:${index}`) for tests and DB-free maths; seed-data.ts was checked against SPEC docs 4–6 and needed no corrections.
