# Decisions

One line per decision the spec did not settle, with the reason. Newest sections at the bottom.

## Stack and environment (milestone 0)

- D001 Stack changed by Nahom mid-build (prompt updated on main): Railway Postgres + Drizzle, Better Auth, Railway Bucket (S3 API), Railway cron. No Supabase, no Supabase shim, no RLS-on-auth.uid(). Reason: all infrastructure on Railway and GitHub only.
- D002 No Supabase scaffolding had been created before the change (only Next.js + shadcn/ui), so nothing needed removing.
- D003 Libraries used instead of hand-rolled code (Nahom's instruction): date-fns-tz for Addis time, React Hook Form + Zod for forms, TanStack Table for staff lists, browser-image-compression for photo uploads, Better Auth for auth, password hashing and sessions, AWS S3 SDK presigner for signed URLs.
- D004 Next.js pinned to 15.5 (App Router, React 19). Reason: stable, well-known APIs; Next 16 adds churn with no benefit here.
- D005 `.npmrc` sets `legacy-peer-deps=true`. Reason: better-auth declares optional peers for other frameworks (SvelteKit wants vite 8) that clash with vitest's vite range; none of them are used.
- D006 Local database: Docker is available in this environment (daemon started manually), so `scripts/db-start.sh` runs `postgres:16-alpine` in Docker on port 54329. Fallbacks in order: a local Postgres 16 install (`pg_ctl`), then PGlite through `@electric-sql/pglite-socket`. Same Drizzle migrations everywhere.
- D007 Files: `STORAGE_DRIVER=local` (default in dev/test) stores files under `.data/storage/` and serves them through an HMAC-signed, short-lived route; `STORAGE_DRIVER=s3` uses the Railway Bucket with presigned GET URLs (5 minutes). Every read goes through an authorization check before a URL is issued.
- D008 The browser never talks to the database or the bucket directly. All reads and writes go through server components, server actions and route handlers, which call `src/server/authz/` and then services. Reason: one enforcement point; no secrets or SQL client in the bundle; less JavaScript on 3G.
- D009 Business logic lives in services (`src/server/services/`) that take `(ctx: { db, actor, now })` so the same code runs from server actions, job routes, tests and the week simulation with a fake clock.
- D010 Project subagents are written to `.claude/agents/`; because agent definitions load at session start, this session runs them as general-purpose subagents briefed with the exact content of those files.

## Auth and roles

- D011 Staff sign in with email + password (Better Auth emailAndPassword). Clients sign in with phone number + password through Better Auth's phone-number plugin with `requireVerification: false` (no SMS). Each client user gets a synthetic, non-deliverable email `<e164 digits>@clients.questmeals.invalid` because Better Auth requires an email column.
- D012 Staff reset a client's password from the client page; the new password is hashed with Better Auth's own password hasher (`ctx.password.hash`) and written to the client's credential account. No hand-rolled crypto.
- D013 Roles are a text array on the user (`owner`, `operations`, `nutritionist`, `kitchen`, `delivery`, `coach`, `client`). "Coach" is modelled as a role in the set because the spec calls Dagi and Kidus owners "flagged as coaches"; a flag in the role set is the same thing and keeps one permission check.
- D014 Better Auth user ids are UUIDs (`advanced.database.generateId: "uuid"`), stored as `uuid` columns so every table keys on UUIDs.

## Domain interpretations (milestone 0, see PLAN.md section 7)

- D015 Cook date = drop date. Daily and three-drops clients get each service day cooked that day; Sunday's meals are cooked and dropped Saturday when Sunday is not a service day (`sundayWithSaturday`, default on, because the spec's rotation includes Sunday C).
- D016 Only daily delivery and pick-up are enabled by default, matching the package table. Three-drops and every-3-days can be enabled by an owner. Weekly delivery stays in the pricing table (4.33 drops) but cannot be enabled while the freshness rule is 3 days, because a weekly drop would break "delivered no more than 3 days after cooking".
- D017 Quick-start period: from the start date to the end of the week that the first weekly cutoff after the quick-start lock will lock. Example: paid Friday → starts Saturday and is billed through the end of next week, because next week was already locked on Thursday. This extends "service days left in the current week" so a late-week quick start never falls between cycles.
- D018 Quick-start capacity counts reserved starts (issued or paid quick-start invoices) per start date; a full date pushes to the next service date with room.
- D019 When a quick-start payment is confirmed after the 18:00 lock it was quoted for, the start moves to the next available date, the period is recomputed and any difference is kept as an account credit (or amount owed) applied to the next invoice.
- D020 Unpaid = not cooked, per day: at a lock, a meal day is included only if a paid invoice covers it; a week with no covered day is `skipped_unpaid`.
- D021 Billing periods: weekly invoices cover Monday–Sunday; monthly invoices cover calendar months from the start date. Full month = plan price − monthly discount; any other period = round to nearest 10 of (plan price − discount) × service days ÷ 26. The next period's invoice is generated at the Thursday lock that precedes the cutoff it is due at.
- D022 Subscription term defaults to 1 month (1–4 allowed); renewal extends the end date by the term (automatic renewal is phase 2). Price locks for 4 months from the subscription start.
- D023 Body weight stored as integer grams; age stored as entered at intake (whole years).
- D024 Base recipe amounts are numeric with one decimal (the spec has 13.5 g oil); profile portions, stock and purchases are integer grams or pieces.
- D025 On-time delivery = drop marked delivered on its drop date at or before the delivery deadline setting (default 12:00 Addis).
- D026 Savory snack alternative uses 2 eggs, 100 g cucumber and mitmita (seasoning); the cucumber weight was not in the spec.
- D027 Extra protein add-on is a standing add-on per meal slot (applies to that slot's meal every day), priced per portion with the spec formula and added to the client's food cost.
- D028 Gomen → mixed sautéed veg is seeded as cabbage 60% / carrot 40% of the same grams (the Menu A side ratio is 120:80).

## Database, seed, auth and authz (milestone 1, db-engineer)

- D200 (db) `ingredients.slug` (unique, not null) added as the natural key of the reference seed so seeds are idempotent and code/tests can find "chicken-breast" without relying on display names. PLAN.md updated.
- D201 (db) `meals.pantry text[]` holds the recipe-card pantry list from the seed (awaze, garlic, salt…); pantry items are not tracked in stock. PLAN.md updated.
- D202 (db) `swap_rules.to_ingredient_split` is jsonb `[{ ingredientId, fraction }]` with resolved ingredient UUIDs (not slugs); when present it overrides `to_ingredient_id` (gomen → cabbage 0.6 / carrot 0.4).
- D203 (db) The reference seed is insert-if-missing (`on conflict do nothing` by natural key: area name, ingredient slug, meal code, (meal, part name), (part, ingredient), swap code, package code, settings key). Re-running never overwrites staff edits (prices, settings, packages). Extra unique keys added for this: parts(meal_id, name), part_ingredients(part_id, ingredient_id).
- D204 (db) `profile_portions` are seeded by a stub (`db/seed/portions.ts`, qty = computed_qty = round(base) for all six profiles); the lead replaces it with the domain portion engine.
- D205 (db) Demo prices: real ingredient prices are empty, so the pricing formula cannot price anyone yet. Demo subscriptions use the spec's modelled figures — 58,400 ETB/month daily delivery, 54,100 pick-up — with price_day = round(month / 26) (2,246 / 2,081), plan price = month (service fee 0), and `price_breakdown = { demo: true }`.
- D206 (db) Demo calendar (relative to `today`, default Addis today, tests use 2026-10-19): subscriptions start the Monday of the previous week, term 1 month (end = start + 1 month − 1 day), price lock start + 4 months. Weekly billers get one invoice per Mon–Sun week from the start through the week after today's week (past and current paid with a confirmed payment by Nebiyou, next week issued, due Thursday 18:00 Addis = 15:00 UTC of today's week); weekly amount = round10(plan × 6 / 26). Monthly billers get one paid invoice for the first month. The paused client's paused week is not invoiced and their end date moves 7 days.
- D207 (db) Demo nutrition profiles use Mifflin–St Jeor × activity × goal factor, size = nearest of S/M/L kcal, kcal_target and macros at the size's kcal; set by the nutritionist (Hana), not provisional.
- D208 (db) `seedDemo` is skipped when the first demo staff user already exists, so `db:seed` can be re-run safely. `removeDemo` deletes in one transaction: demo/demo-authored community posts, challenges by demo users, demo partner contributions, demo purchases/stock counts, everything of demo clients (orders, drops, invoices, payments, subscriptions, check-ins; the rest cascades), then demo users (sessions, accounts, notifications, Telegram links, comments, reactions, reports, mutes cascade).
- D209 (db) Foreign keys: client-owned rows cascade on client delete; "who did it" user references (`*_by_user_id`, `confirmed_by`, `rider_user_id`, …) are nullable with `on delete set null`, so deleting a (demo) user never blocks on history; reference rows (ingredients, meals, packages) are `restrict`.
- D210 (db) Better Auth rows are written by our own helpers (`createStaffUser`, `createClientUser`, `setUserPassword` in `src/server/auth.ts`) exactly as Better Auth does on sign-up (user + `credential` account with accountId = user id), hashing with `(await auth.$context).password.hash`. Emails are stored lower-case. Client users get phone_number (E.164 `+2519/7XXXXXXXX`) and roles ['client']; the phone validator rejects anything else at sign-in.
- D211 (db) `user.roles`, `isDemo` and `banned` are Better Auth additional fields with `input: false`, so sign-up endpoints can never set roles; `loadActor` returns null for banned users.
- D212 (db) Permissions are fine-grained string keys (`PERMISSIONS` in `src/server/authz`). Interpretations of PLAN §4: swap approval (`swaps.approve`) is owner + nutritionist (spec: anything outside the table needs nutritionist approval; owners see all records); `orders.lock`/`orders.write` are operations only (owners read orders); stock counts and waste are operations + kitchen, purchases operations only; anon may only read the public calculator settings, packages, and create a lead via sign-up. Community access for clients still needs the domain `communityAccess` check on top of `community.*`.
- D213 (db) `homePathFor`: owner → /staff/dashboard, operations or nutritionist → /staff, kitchen → /kitchen, delivery → /delivery, client → /app, coach-only → /app/community, none → /login.
- D214 (db) `invoices.subscription_id` is not null (quick-start and adjustment invoices also hang off a subscription), keeping unique(subscription_id, kind, period_start) meaningful for job idempotency. `notifications.dedupe_key` is unique but nullable (notifications without a dedupe key are allowed). `order_meals` has unique(order_day_id, slot): one meal per slot per day (the savory snack replaces the snack).
- D215 (db) `db` (db/client.ts) and `auth` (src/server/auth.ts) are lazy proxies created on first use and cached on globalThis (survives HMR), so importing them never opens a connection or needs DATABASE_URL at build time. Tests and scripts use `createDb(url)` / `createAuth(db)`.
- D216 (db) Migrations live in `db/migrations` (0000_init generated by drizzle-kit, no hand-written SQL needed: the partial unique index and the coalesce expression index are expressed in Drizzle). `db/migrate.ts` resolves the folder from the repo root (cwd).
- D029 Extra-protein add-on: the per-portion price (spec formula, rounded up to 10) is what the client sees when choosing it; billing uses the plan price, whose food_day already includes the add-on grams as the pricing formula says ("plus swaps and add-ons"), so nothing is charged twice. Adding or removing an add-on re-quotes the plan from the next lockable week.
- D030 Swaps from the swap table within the package limit are approved immediately (status approved); requests outside the table go to the nutritionist (status requested) and do not count toward the limit until approved.
- D100 (domain) `time.ts` does `DateStr` arithmetic on UTC epoch days (no `Date` local getters), so dates never depend on the process time zone; date-fns-tz is used only for instant <-> Addis conversion and formatting. Tests re-run the key assertions under five process time zones.
- D101 (domain) `suggestNutrition` returns integers for storage: bmr, tdee and the goal-adjusted `targetKcal` rounded; macro grams are computed from the chosen size's kcal (what the kitchen cooks), not from the raw target. `bmr`/`tdee`/`goalKcal` stay unrounded (1345.25 for the reference woman).
- D102 (domain) Portion solver: weighted least squares on four rows (day kcal, protein g, carb g, fat g), each weighted 1 / (target × tolerance), with each group factor boxed to [0.6, 1.8]; all 27 free/min/max assignments are solved and the best feasible kept (exact "clamp and re-solve"). Then piece parts are rounded and the gram parts re-solved around them, then clamp-aware rounding (nearest 5 g / whole piece that stays inside 0.6–1.8 × base, e.g. 7 g oil at factor 1.8 -> 10 g not 15 g; a single whole egg always stays 1) and a one-step local search on that grid. Flagged when the rounded day misses ±3% kcal or ±10% on any macro grams. With the seed recipes 7 of 24 are flagged (A S_BUILD, A L_BUILD, B L_BUILD, C M_BUILD, C L_LEAN, C L_BUILD, D L_BUILD): the carb group hits 1.8 (or fat 0.6) before the target is reached, so the nutritionist must edit those cells.
- D103 (domain) Manual portion cells are kept exactly (even outside the clamp) and treated as fixed in the solve; `computedQtyByPartId` for a manual cell is the solver's value for that cell with no manual cells, so the profile table can show both.
- D104 (domain) Quick-start period end = the day before `nextLockableWeek(lock)` where lock is the daily 18:00 lock the evening before the start date (≥ the payment deadline `lockAt`). This follows D017's example (Friday -> through the end of next week) rather than the literal "Sunday of the week locked by the first cutoff after the lock", which would bill one week too many and overlap the client's first weekly order. A lock at exactly Thursday 18:00 is not part of that weekly lock.
- D105 (domain) Monthly billing periods are one-month periods anchored at the start date (22 Oct – 21 Nov), the last clipped to the end date and prorated; a quick-start client's regular billing anchors at quick_start_period_end + 1. `nextInvoicesToGenerate` also returns earlier periods that were never invoiced (catch-up), skips periods with a non-void invoice of the same start and kind or fully covered by other invoices, and sets due = the cutoff of the week the period starts in.
- D106 (domain) Swap quantities: `fixed` and `add` amounts are base amounts scaled by the replaced part's profile ratio (qty ÷ base qty) and rounded to 5 g (2 injera -> 90 g rice; 50 g beans at base 40 -> 75 g beef); `multiply` is exact; `same` keeps qty and unit. Swapped items are named "Original → New" (add: "Beans → extra Lean minced beef") so production rows separate them. Order: slot rules (replacement meal at the client's profile portions, else base) -> ingredient rules by sort (an item made by a swap is not swapped again) -> add-ons (extra protein follows the swapped main protein). Main protein = the gram protein/dairy item with the most grams; a meal without one gets no add-on.
- D107 (domain) Pricing prices seasonings (stevia, cinnamon, milk…) like any ingredient, so a missing seasoning price also blocks publishing ("every ingredient in that client's menu"). Egg whites are costed and buffered as eggs. `priceDayBirr` = Math.round(price_day); price_month rounds the unrounded price_day × 26.
- D108 (domain) `countStandingSwaps` counts swap-table swaps (rule id set) that are approved or requested and in force that week; custom requests never count (compatible with D030). `checkSwapRequest` also answers `duplicate` for a rule already standing.
- D109 (domain) Allergy/dislike matching is case-insensitive at a word start, with the term's singular and a synonym map (fish->tilapia, nuts->peanut, dairy/lactose->yogurt/ayib/feta/mozzarella/milk/cheese, egg->egg whites, gluten/wheat->bread/tortilla/pasta/lasagna, meat->beef/chicken, legumes->beans/peanut, spicy->mitmita/awaze). It checks ingredient names, part names (for swapped items only the new side) and, when nothing else matched and no swap removed the term, the meal name (e.g. "chili"). Oats are not treated as gluten. Over-matching (e.g. "egg" vs "eggplant") is accepted as the safe side.
- D110 (domain) `lockWeek` leaves out cancelled/ended subscriptions and those whose dates miss the week; days that already have an order day (quick start) are not rebuilt; every-3-days clients cook on their group's drop date; eat-by is computed after swaps (tilapia swapped to chicken -> + 3 days).
- D111 (domain) Shopping buys are rounded up to 0.1 kg / 0.1 litre (litre via grams per unit: oil 920, milk 1030) and whole pieces; line cost = buy units × price rounded to whole birr, null = "price missing"; lines fully covered by stock are omitted unless asked for.
- D112 (domain) KPIs: new = clients whose first non-cancelled subscription starts in the month; churn rate = churned ÷ (active + churned − new); MRR = Σ (plan − discount) of active non-quick-start subscriptions; invoiced = non-void invoices issued in the month; collected = payments confirmed in the month; delivery cost = delivery (not pick-up) drops in the month × drop cost; on-time is over delivery drops dated up to today; "no check-in for 14 days" counts from the start date when a client never checked in.
- D113 (domain) Community roles combine by taking the highest level; a mute caps client-derived access at react and does not affect staff access; an ended member keeps read + react through ended_at + 14 days inclusive.
- D114 (domain) Brand contrast (WCAG 2.x) is asserted in `contrast.test.ts`: accent #C2410C on white 5.18, white on accent 5.18, #171717 on white 17.93, #525252 on white 7.81, #FAFAFA on #0A0A0A 18.97, #FB923C on #0A0A0A 8.75 — all AA.
- D115 (domain) `seed-domain.ts` maps the seed reference data to domain types (ids = slugs / meal codes, part ids `${code}:${index}`) for tests and DB-free maths; seed-data.ts was checked against SPEC docs 4–6 and needed no corrections.
- D031 seedPortions now runs the real portion engine (recompute + upsert); its idempotency test checks the profile_portions row count instead of 'inserted = 0' (the stub's behaviour).

## Spec review fixes (milestones 1–2)
- D032 Unpaid quick-start sign-ups with no receipt are cancelled 72 hours after sign-up (their invoice voided), so abandoned sign-ups stop holding quick-start capacity.
- D033 "Paid" at a lock means fully covered by payments confirmed at or before that lock's instant (Thursday 18:00 for the weekly lock, 18:00 for the quick-start lock). Late confirmations and re-runs never change a lock that already happened.
- D034 Paused weeks are never invoiced; a pause voids a weekly invoice inside it (paid ones become account credit) and reduces or credits a monthly invoice by the paused service days. Voiding an invoice returns any credit it had used.
- D035 Creating a plan immediately issues the invoices the next Thursday lock needs (e.g. a quick start's first regular week), due at that week's cutoff.
- D036 Allergies and dislikes are also checked against each meal's pantry items (garlic, awaze, lemon …).
- D037 Swaps with extra cost "0" in the swap table do not change the client's price; only "price difference" swaps and add-ons are included in food_day.
- D038 Better Auth public sign-up endpoints are disabled; accounts are created only by our services. BETTER_AUTH_SECRET is required in production.
- D039 Deleting a user that has partner contributions is refused (restrict), so the partner log is never lost.

## Community (milestone 4, ui-builder community)

- D420 (community) Pinned posts are returned as their own list on the first feed page only (not paginated; they are few); the rest is paginated newest first with a (created_at, id) cursor that carries Postgres' own created_at text so microsecond precision never repeats or skips a post. Page size is settings.community.pageSize.
- D421 (community) Hidden posts and comments are visible (greyed, with the reason) only to moderators (owner, operations); coaches and members never see them, and a hidden post's page is "not found" for them. Comment counts follow the same rule.
- D422 (community) Hiding a reported item resolves every open report on it; "Dismiss" resolves one report and writes an audit row (community.report.dismiss). Hide, unhide, mute and unmute all write audit rows (DATA-03).
- D423 (community) A mute writes a community_mutes row and also sets clients.community_muted_until; access uses the later of the two. Unmute ends open mute rows at now and clears the client column. Mutes are 1, 3 or 7 days from the staff screen (service accepts hours/days up to 90 days); a reason is required.
- D424 (community) Report alerts go to users with the operations role (in-app + Telegram "now"); replies, announcements, new challenges and challenge reminders are in-app at once and Telegram "digest". Dedupe keys: community-report:<reportId>, community-reply:<commentId>, community-announcement:<postId>, community-challenge:<challengeId>, challenge-reminder:<challengeId>:<addisDate>. Replying to your own post does not notify you.
- D425 (community) "Active members" for announcements and reminders = clients with status active and an app account. Paused, ended and muted members do not get challenge reminders.
- D426 (community) Sharing progress needs at least two weigh-ins in the member's own check-ins; ticking "share my progress" without them is a specific error rather than a silent post without numbers. The checkbox is disabled in that case.
- D427 (community) Challenge check-ins need full access (paused/ended/muted cannot join), happen once per Addis date, and only between starts_on and ends_on inclusive. The streak shown after a challenge ends is counted up to its last day. Leaderboard shows the top 20 by days completed, ties share a rank.
- D428 (community) New posts with photos go through a route handler (POST /app/community/posts, multipart) instead of a server action, so four compressed photos (~0.5 MB each) fit without raising the 1 MB server-action body limit. Photos are compressed in the browser to JPEG, max 1600 px long edge, ~0.5 MB.
- D429 (community) Coaches who are not also clients post with their staff name split into first name + last initial ("Dagi B."); members use clients.first_name/last_name. People lookups select only name, image key and roles — never phone, email or address (SEC-13).
- D360 (kitchen) Kitchen sheets read only order meals whose weekly order is `locked` (weekly and quick start); quick-start portions are counted per production row ("QS n") from `order_days.is_quick_start`, and the cook-day picker shows today, tomorrow and every cook date with locked meals in the next 14 days.
- D361 (inventory) Stock model: a stock count is the quantity at the END of its count date (that day's purchases, waste and cooking are already in it). On hand at the end of day E = last count on or before E + purchases, − waste and − usage of locked meals cooked strictly after the count up to E, never negative. The shopping list for week W uses on hand at the end of W − 1 (Sunday), so a Sunday count and Saturday purchases both reduce it. An ingredient never counted starts from 0 plus its full purchase history.
- D362 (inventory) The morning top-up list buys the whole fresh need (chicken, beef, fish, eggs, dairy, vegetables, fruit) of the quick-start meals of that cook date without subtracting stock, because the weekly list was sized before those clients were locked.
- D363 (inventory) Purchases, stock counts and waste are entered in purchase units (kg, litre, pieces) and stored as grams / pieces (litre × grams per litre: oil 920, milk 1030). Unit cost from a purchase = round(total price ÷ quantity in purchase units); it overwrites `ingredients.cost_per_unit_birr` (and the supplier when given), adds an `ingredient_prices` row (source purchase) and an audit row `ingredient.price.purchase`. Egg whites and untracked items cannot be bought or counted directly (the error names the stock item, e.g. Eggs).
- D364 (inventory) "Matches expected" on a stock line stores the server's exact expected quantity (not the rounded number shown); saving again on the same date replaces the count (unique per ingredient and date). Counts and purchases cannot be dated in the future.
- D365 (inventory) Prices are for owners and operations only: the shopping list, top-up list, purchase log and price history refuse kitchen staff (who hold `stock.read`), and kitchen-facing ingredient lists carry no price.
- D366 (delivery) Riders (delivery role without operations/owner) see only today's delivery-kind drops that are assigned to them or unassigned; a rider who marks an unassigned drop delivered or failed becomes its rider. Kitchen staff can read drops but get no phone or address (`clients.readDeliveryContact`).
- D367 (delivery) Reordering accepts all of a day's delivery drops or one area's drops: the given drops take the slots those drops held in the current order and the whole day is renumbered 1..n (so the seeded `area sort × 1000` positions become 1..n on the first save). Drag and drop works within an area; up/down buttons do the same for keyboard and touch.
- D368 (delivery) Failed reasons: Not home, Wrong address, Refused, Other (+ text, stored as "Other: …"). Each failure notifies operations once (dedupe key includes the instant), linking to `/staff/delivery?date=`. Statuses can be changed again on the same day (a failed drop can still be delivered).
- D369 (kitchen) Packing list marks "Pack injera separately" for any client whose meals that day contain injera, shows delivery area or "Pick-up at the cafe", and outlines the whole client block in red when any allergy / dislike conflict is left after swaps.

## Client app, calculator and sign-up (milestones 3–4, ui-builder client)

- D390 (client) Sign-up creates the account in a server action (`createClientUser`, D038) and then signs in from the browser with `authClient.signIn.phoneNumber` before redirecting to /app/payments; no session cookie plumbing in the action. If that sign-in fails the user is sent to /login with their account already created.
- D391 (client) `signUp` is for signed-out visitors only (anon passes via PUBLIC `clients.createLead`); a signed-in actor gets "Sign out first". Self-service plans are 1-month terms; other terms are set by staff.
- D392 (client) A staff-entered lead with the same phone and no login (status lead) is claimed by the sign-up (fields updated, no duplicate record); its existing current nutrition profile is kept, otherwise a provisional one is created (set_by null). A phone with a login or a non-lead client gets "This phone number already has an account — sign in."
- D393 (client) Address/area/landmark changes are saved at once: drops of an already-locked week were created at the lock with an address snapshot, so the new address is used from the next lockable week (shown to the client). Address changes are audited.
- D394 (client) "Request a size change" stores no new table: it notifies every nutritionist (dedupe per client per Addis day) and writes an audit row `nutrition.size_change_requested`; the profile is unchanged (NUT-07).
- D395 (client) Meal ratings upsert on (client, meal, service date): rating again the same day changes it. Allowed only for meals on a locked order of that client with service date ≤ today; comment ≤ 500 chars; private (only mealRatings.read staff and the client).
- D396 (client) Client weight log: one client entry per date (re-logging updates it), today or up to 60 days back; nutritionist check-ins are separate rows.
- D397 (client) Ending a swap or an extra-protein add-on takes effect from the next lockable week; withdrawing a pending custom request ends it at once. Swap screen lists only swap-table rules that touch at least one meal on the menu.
- D398 (client) Calculator indicative price = `quotePrice` for the suggested profile, Essential, daily delivery (server action, anon); when any ingredient price is missing no number is shown ("Prices are being updated — we'll confirm your price at sign-up"). Sign-up step 5 shows plan price and the quick-start first payment from `previewQuote`.
- D399 (client) Telegram webhook: timing-safe compare of `x-telegram-bot-api-secret-token` with TELEGRAM_WEBHOOK_SECRET; if the secret is unset every request is refused (401). Only `/start <32-hex token>` is handled; the reply is sent with `sendTelegram`. Connecting from the profile also sets `clients.telegram_opt_in`; disconnecting clears it.
- D400 (client) Receipts: Telebirr and CBE need a transaction reference and a photo (compressed in the browser to ≤ 1600 px / ~0.5 MB); cash needs neither (confirmed at the counter).
- D300 (ops) Client payment status for the list and client page: none = no non-void invoices; overdue = an issued invoice whose due time has passed; due = an issued invoice not yet due; paid = every non-void invoice paid. Shown only to roles with invoices.read (the nutritionist sees "none").
- D301 (ops) Client edits: body stats and notes need clients.writeBodyStats (owner, operations, nutritionist); any other field needs clients.write. Only changed fields are saved and audit-logged (before/after). Address, area, landmark, allergies and dislikes take effect from `changeEffectiveWeek` (already-locked weeks keep their drop address snapshot); the toast names that week.

## Final spec review fixes
- D052 A week skipped for non-payment comes off the invoice that billed it at the lock (weekly invoice voided; other invoices reduced by those service days). The client is never asked to pay for a week that was not cooked; the engine test that paid a skipped week late was changed to expect the invoice to be cancelled.
- D053 A receipt confirmed for an invoice that was cancelled meanwhile (pause or skip), or for more than a reduced invoice now asks, is confirmed and the extra money becomes account credit for the next invoice. A pause that takes more off an invoice than it still asks marks it paid and credits the surplus.
- D054 Plan repricing stores the choices its price reflects (`price_breakdown.pricedChoices`) and prices each change against those, so two changes in one week are counted once each and a withdrawn change is taken back.
- D055 Approved custom swaps (no swap-table rule) are written on every locked meal as "Kitchen note: …" next to conflicts, so they appear on the packing list, order review and client page; the dashboard's allergy-conflict count ignores kitchen notes.
- D056 Telegram goes to a client only while their "Send me notifications on Telegram" switch is on; linking Telegram from the app turns it on. Staff always receive Telegram once linked.
- D057 The quick-start lock skips weeks the client paused, so the order of the two 18:00 Thursday jobs never matters.
- D058 Renewing a plan after its 4-month price lock prices the new term from the current formula and locks it again from the renewal (audited as price.renewal); during the lock, renewal keeps the price.
- D059 At the Thursday lock, every service day the plan covers but the lock does not cook (a skipped week, or the unpaid part of a week at a billing boundary) comes off the invoice that billed it. Each client's lock (order, days, invoice reduction) runs in one transaction, so a run that stops partway is redone cleanly.
- D060 A receipt waiting for an invoice that a pause, skip or credit brought to 0 is confirmed and kept as credit; only a true duplicate (other confirmed receipts already cover the invoice) is refused.
- D061 Renewal re-prices only once the price lock has ended. A renewal inside the lock keeps the price and marks the plan; the daily 09:00 job re-prices it on the lock's end date and locks it again for 4 months from that day. Quotes use the swaps and add-ons in force from the next lockable week, so changes already made are never dropped.
- D062 The client Telegram switch applies to client-facing notifications (links into /app); staff alerts (links to /staff, /kitchen, /delivery) reach a linked coach or owner who is also a subscriber regardless.
- D063 The renewal test now expects the lock to restart from the re-pricing day (25 Oct → 25 Feb) rather than the renewal start, matching D061.
- D064 Days taken off an invoice (pause, skip) are valued at that invoice's own daily rate ((amount + credit applied) ÷ service days), not today's plan price, so a re-price, discount or add-on change mid-period never over- or under-credits.
- D065 Invoice generation never bills a service day in a week that is already locked unless that day was cooked: skipped days, and weeks a late renewal missed, are not billed; billing resumes with the next lockable week. Renewing a plan issues the next periods' invoices at once, due at their cutoffs.
- D066 Renewal reminders: the client gets "Plan ends in N days" (link /app/plan); operations get a separate staff alert linking to the client page, so a staff member's client Telegram switch never hides it.
- D067 Taking days off an invoice removes the value from the invoice amount first and then from the credit applied to it; both parts are kept in step with the remaining days, so repeated reductions or a later void return exactly what was put in (credit) or paid.
- D068 A negative credit applied to an invoice (money the client owes, e.g. a moved quick start) is never given back by a reduction; it stays on the invoice and a void returns it. Pausing is serialised per plan (subscription row and invoices locked for update), so a double tap or a payment confirmation at the same moment cannot double-reduce an invoice or act on a stale row; the Thursday lock also locks the invoices it reduces.
- D069 e2e/staff-settings.spec.ts waited for nothing before reading the swap-table inputs and once read them empty before hydration (1 failure in 257 on a clean-clone run). The test now waits for the inputs to have values; the assertion itself is unchanged.
- D070 The Thursday lock and a last-second pause are serialised on the plan row: each client's lock transaction locks the subscription and re-reads its pauses (a pause that committed first makes the week paused), and pausePlan refuses a week that already has a weekly order (the lock committed first). The quick-start re-plan voids later invoices under the same locks and credits only invoices it actually voided.
- D071 The quick-start lock adds a period inside a transaction that locks the plan row and re-reads its pauses (same as the weekly lock), so a last-second pause is either honoured or refused, never both. confirmPayment takes locks in the same order as every other money path (payment → subscription → invoice), removing a deadlock with the Thursday lock for plans waiting for their first payment.
- D072 Moving a missed quick start keeps any extension the plan already had (paused weeks) and does all its writes under the plan lock on fresh rows; if the invoice or a receipt changed meanwhile, the next run decides. Lock order across money paths is client → subscription → invoice (confirmPayment, swap/add-on repricing), subscription → invoices (pauses, Thursday and quick-start locks, invoice generation); renewPlan and repriceForPlanChange lock and re-read the plan row before writing.
- D073 Client-row locks use FOR NO KEY UPDATE so they never block the foreign-key checks of inserts (pauses, orders, invoices, credits) and cannot deadlock with plan-row locks. A moved quick start bills only days it will cook (stops before any week the Thursday lock already decided; paused weeks unbilled) and never adds days under a decided week. The Thursday lock runs the quick-start lock first, so the 18:00 outcome is the same whichever cron fires first. repricePlan, the renewal re-price, plan expiry and quick-start expiry all act on rows locked and re-checked in their transaction.
- D074 The quick-start lock treats as decided only weeks of the same plan; a returning client's quick-start days go into the client's existing row for that week (one weekly order per client and week), taking it over when the old plan left it skipped or paused, so every paid day is cooked. 'Already added' is detected by the client's quick-start days inside this plan's own period.
- D075 Each order day records the delivery option of the plan that ordered it (order_days.delivery_option, migration 0003). Drops and kitchen packing use the day's option, falling back to the week row's, so a returning client's quick-start days in a week their old plan locked are packed and delivered per the new plan.
- D076 A billing period lengthened after it was invoiced (renewal or pause moved the plan's end date) bills only the uncovered remainder, as its own prorated invoice starting the day after the existing invoice ends, due at the cutoff of the week it starts in. The original invoice is never changed, so a paid invoice stays as paid.
- D077 The invoice unique key (subscription, kind, period start) applies only to non-void invoices (partial unique index, migration 0004). A period whose invoice a pause voided is billed again when the plan later extends past the pause, so the promised days can be paid and cooked; there is still at most one live invoice per period start.
- D078 Invoice generation bills, for each period, only the days no non-void invoice covers, one invoice per uncovered run (generalising D076). Re-billing a period after its short invoice was voided (D077) therefore never bills days a live remainder invoice already bills: each service day is billed at most once.
- D079 Renewal counts from the plan's start: new end = start + (months so far + term) − 1 day + 7 days per paused week (renewedEndDate). Adding the term to an end date that a short month clipped drifted out of step with the billing months for starts on the 29th–31st, so renewed months were billed as partial months. An end date that does not fit that shape falls back to the old rule.
